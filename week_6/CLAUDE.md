# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**TDES — Training Data Execution System (V5).** A small, fully-deterministic, pure-numpy
training-data pipeline that *proves* what it consumed, why, what was learned, and how to
reconstruct the run. The assignment (`week6_assignment.md`) is graded entirely on
**reproducible evidence**: the grader re-runs the command, checks the generated
`evidence.json`/`evidence.md`/`run.log` against the artifacts, then inspects the code to
confirm nothing was hardcoded or simulated.

## Commands

```bash
python run_demo.py                  # full demonstration -> regenerates submission_artifacts/ (exit 0 iff all pass)
python tests/test_invariants.py     # invariant test suite (also: pytest tests/)
python tdes/assets/build_corpus.py  # regenerate the frozen demo corpus (one-time asset builder)
```

No dependencies beyond **numpy** (torch/tokenizers are deliberately NOT used). `run_demo.py`
takes ~60s; it runs training ~5× (main + resume proof's reference/crash/resume + fork parent).

## Architecture (the big picture)

The pipeline: `documents → tokenized shards → manifests → mixture schedule → packing →
batches → training → consumption ledger → learning ledger → checkpoint → crash → resume →
replay → audit`. Everything lives in `tdes/` (see README.md for the per-module table).

**The one invariant that explains every design choice:** a batch is a pure function of
`(seed, mixture schedule, step)`, and all evidence is computed from real hashes/ledgers at
runtime. Consequences that will bite you if you forget them:

- **Determinism is load-bearing.** `batch.build_batch` uses a counter-based RNG on
  `(seed, step)` and visits lanes/shards in sorted order. Resume rebuilds batch `#offset`
  deterministically, so checkpoints store the ledger offset, not RNG state. Anything that
  makes batch construction depend on wall-clock, dict iteration order, or float
  non-determinism breaks resume AND replay.
- **OPUS depends on model state**, so its proxy direction is recomputed each step (a pure
  function of current params) — otherwise resume (which reloads model-state-at-offset) would
  diverge. See the `set_context` recompute in `opus.py` and the note in `train.py`.
- **Fresh runs must clear stale artifacts.** `shard.build_shards` clears old shards;
  non-resume `run_training` calls `checkpoint.clear()` and `ledger.reset()`. A stale
  `ckpt_*.json` from a prior run will be mistaken for "latest" otherwise.
- **Floors are on TOKEN share, not draw count.** Doc lengths vary hugely by lane, so
  `batch.build_batch` targets `weight × capacity` tokens per lane. `mixture.floored_weights`
  aims a margin (`ENFORCE_MARGIN`) above the true floor so per-window variance still lands
  above the floor the audit checks.
- **Docs are chunked to ≤`shard.CHUNK` (28) tokens** so every span fits a sequence (no
  packing truncation) and lane token-balancing is possible. Decontamination regroups chunks
  by base doc id (`firewall._docs_by_lane`) so it compares whole docs, not chunks.

## Frozen inputs (never regenerated by the demo)

`tdes/assets/tokenizer.json` (byte-level BPE, vocab 10000, from week2) and
`tdes/assets/corpus.jsonl` (4 lanes: real web+indic from week4, synthetic code+math). Their
identities are hashed; the whole `submission_artifacts/` tree is rebuilt from them.

## Verifying changes

Any change to batch construction, packing, the model, or the mixture must keep
`python tests/test_invariants.py` green — especially `test_gradient_check` (model backward),
`test_no_cross_document_attention` (packing), `test_reproducible_batch_stream`, and the
resume/replay/fork proofs. These are the invariants the grade depends on.
